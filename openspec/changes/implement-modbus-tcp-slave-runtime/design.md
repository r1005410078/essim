## Context

现有core运行协调器是契约，配置目录仅内存；libmodbus-rs持有线程绑定的C句柄，TCP receive是同步接口。不能按1000端点及10000连接各建线程，也不能让慢客户端卡住其他端点。

## Goals / Non-Goals

Goals：真实TCP基础四区读写及连接管理；配置／运行值分离；清晰的运行命令、事件、查询；可验证启停、权限、并发及记录失败行为。

Non-Goals：RTU及其诊断、额外功能码、配置数据库、历史浏览及可用回放、动态仿真、声称实现1000端点满负载。RTU另提案，M04总览保持未完成。

## Decisions

1. 固定数量工作线程用mio维护监听及客户端事件；端点与Unit始终属于一个工作线程。完整帧由有界MBAP缓冲收集，响应采用有界非阻塞发送；不让C库直接等待外部慢连接。
2. 复用libmodbus 3.2.0的reply及Mapping，通过安全完整帧入口与工作线程私有本地socket pair捕获响应。只扩展安全封装，不手写四区协议栈；C对象在线程内创建和释放，无跨ABI回调。请求形状、映射空洞与外部权限在调用前检查。
3. 运行模型编译为共享Arc，运行值用紧凑四区映射；模型变更不修改已应用快照。现有配置Catalog仍可能深复制，不把运行侧优化描述成全链路亿点容量已达成。
4. 独立运行命令（start／stop／setValues／resetValues）、运行查询及类型化事件按目录组织。配置序号只描述配置，运行修订号独立；只按需查询选中Unit的点值及端点摘要，不推送全量运行值目录。
5. 运行文件记录含起始配置／去重共享模型／独立Unit值、请求及响应与状态，采用有缓冲流式序列化。开放监听前可靠建立记录，写入前可靠记录意图，提交后可靠记录结果；失败停止该端点并保留不确定性。工作台历史／回放后续实施，配置仍不落库。
6. 工程初始边界：固定最多4工作线程、每端点默认10连接（可设置1～100）、全局10000连接、有界控制队列256、每连接输入／输出上限16KiB、请求及发送停滞5秒、停止确认10秒。边界用于拒绝过载与避免无限等待，随实测调整，不是性能SLA。
7. 未知／禁用Unit返回网关目标不可用异常0x0B；未定义地址／禁止写入拒绝整条请求，unsupported功能码异常0x01，非法参数0x03。一次多寄存器写可能覆盖点的一部分，按最终寄存器值解释；非有限浮点拒绝且不产生半写。

## Risks / Trade-offs

- [同步可靠文件写入影响同工作线程尾延迟] → 分层压测披露，不能因追求吞吐关闭录制或静默丢弃；后续按实际结果改为有界独立录制调度。
- [模型／查询深复制导致内存高] → 运行模型共享、按需值查询；配置应用及查询规模单独测量，保留未达标任务。
- [跨平台C库和I/O差异] → 当前验证macOS，Linux及Windows能力按现有封装边界记录，不虚构通过。
- [网络断连无法证明远端收到响应] → 记录实际本地写出和断连，不把本地发送成功解释成远端业务确认。

## Migration Plan

先失败用例、纯运行模型，再封装完整帧、固定线程TCP执行器、可靠记录和配置释放协调，最后Tauri及工作台接入。旧配置命令JSON保持；运行使用独立契约。可通过不装配运行服务回退配置模式，绝不回退假运行。

## Open Questions

EMS实际扫描周期未定；候选1／5／10秒及持续全速仅为压测档位。大规模验收环境、延迟指标及RTU具体子功能后续独立确定。

依据：Modbus V1.1b3、TCP实现指南、libmodbus官方reply文档及仓内固定3.2.0源码；mio 1.2.4官方Poll文档。未明事项以实际测试证据限定。
